GOAL

Build a single-user Windows desktop application called Private Conversation Copilot.

It listens to live meetings/calls as an attendee, maintains conversational context, and privately displays three independent text suggestions.

No meeting bot.
No organizer permissions.
No user accounts.
No cloud database.
No permanent audio recording by default.
No multi-user features.
No installer is required initially.

The first usable version should allow the user to:
1. Launch the Windows app.
2. Enter API keys in Settings.
3. Test those API connections.
4. Choose an STT provider/model.
5. Choose models for suggestion paths A, B, and C.
6. Select microphone and meeting-output audio.
7. Start a session.
8. See a live ME/THEM transcript.
9. Type or paste prepared context and intra-call notes.
10. Automatically detect when THEM finishes a turn.
11. Send the current conversation plus relevant context to the active models.
12. Display three stable suggestion cards.
13. Press Help Me Now to force suggestions immediately.
14. Stop the session cleanly.
15. Review useful local diagnostic information if something fails.
TECH STACK

Use C# with .NET 8 and WPF unless there is a strong technical reason not to.

Use dependency injection and clear interfaces between subsystems.

Use NAudio where appropriate for Windows audio capture. Use native Windows APIs/PInvoke where NAudio does not provide required functionality.

Use async/await, CancellationToken, and explicit request/version IDs for concurrent work.

Use DPAPI/ProtectedData CurrentUser for local API-key encryption.

Use simple local files under the user application-data directory for non-secret settings and session configuration. Do not introduce a database unless it becomes necessary.

Create a GitHub Actions workflow using windows-latest that:
- restores dependencies
- builds the solution
- runs automated tests
- publishes a self-contained win-x64 build
- uploads the published application as a GitHub Actions artifact
This allows the application to be built even if the Codex environment itself is not Windows.

MIDDLE COLUMN

This is the primary visual area.

Display three vertically stacked suggestion cards.

Do not use large A/B/C headers.

Normal card appearance should contain only:
- suggestion text
- small Copy control
- small Dismiss control
Do not permanently display prompts, grounding explanations, model names, token counts, or debug text inside the cards.

Such metadata may be available in debug mode or a tooltip/details view.

Top card = fast/grounded path.
Middle card = reasoning/risk/angle path.
Bottom card = audio-native Realtime path.

Cards must remain visually stable once committed.

Never stream changing model tokens directly into the visible committed card.

A card is replaced only when a later turn is committed.

Dismiss hides the current card only. The box remains active and should generate again on the next committed turn.

Provide clear but unobtrusive idle, working, disabled, and error states.

PREPARED CONTEXT AND RETRIEVAL

Do not send the entire context box blindly on every request.

Split the context into usable chunks.

For the MVP, use a lightweight local retrieval approach that does not require another paid embedding API.

Keyword/BM25/TF-IDF-style relevance is acceptable.

Retrieval should use:
- the current THEM turn
- recent transcript
- current topic
Retrieve only the most relevant chunks within a configurable context budget.

Keep transcript depth and retrieved-context depth as separate concepts.

Retrieved-context depth can live primarily in Settings rather than occupying main-screen space.

TURN DETECTION

Turn detection must be a separate service.

A transcription final is not automatically equivalent to conversational end-of-turn.

Use three signals:
1. Acoustic gate
   Pause / speech-energy indication from THEM.
2. Semantic gate
   Does the current utterance appear conversationally complete?
The first implementation may use reliable local heuristics based on transcript structure, punctuation, question form, incomplete phrases, etc. Keep this behind an interface so a stronger semantic detector can replace it later.
3. Fallback timeout
   Do not wait indefinitely.
Expose reasonable sensitivity/default settings.

When the detector commits an end-of-turn for THEM:
- create a unique turn ID
- freeze the transcript version used for that turn
- finalize suggestion work for all enabled boxes
If THEM resumes quickly after a commit, record that as a probable false endpoint for diagnostics.

HELP ME NOW

Help Me Now must immediately create a turn/suggestion event using the newest available transcript and context.

It should trigger all currently active suggestion boxes concurrently.

It must not wait for normal end-of-turn detection.

PROMPT ASSEMBLY

For text models, construct requests in this logical order:

System behavior instructions

Static Summary

Current structured Meeting State

Rolling discussion summary

Recent verbatim ME/THEM transcript within the selected budget

Relevant retrieved Context

Evidence metadata where useful

Current THEM turn

Box-specific task instruction

Keep prompts concise.

Do not repeatedly include irrelevant context.

BOX A

Independent text inference path.

Purpose:
Fast, practical, grounded response suggestion.

Use an OpenRouter text model.

It should favor:
- direct answer
- useful next question
- prepared context
- factual grounding
- short speakable language
Do not write essays.

BOX B

Independent text inference path.

Also use OpenRouter initially.

It may use a different model and larger reasoning/context budget.

Purpose:
Identify:
- stronger reasoning
- risk
- objection handling
- overlooked angle
- caveat
- alternative response
It should still produce short speakable output, not analysis paragraphs.

A and B must be concurrent and independent.

They must never wait on one another.

The same model/route may be selected for both.

BOX C

Independent audio-native path.

Use the current supported OpenAI Realtime API and a current supported Realtime model verified from official documentation.

Box C maintains its own active Realtime session, but the application remains the source of truth for meeting history.

In Clear mode:

Prefer feeding THEM audio directly to the Realtime session so it can use audio/prosody information.

Inject finalized ME transcript/history and shared meeting state as text/context so Box C remains aware of both sides of the conversation.

Also provide:
- Static Summary
- relevant Meeting State
- relevant retrieved context when appropriate
Do not rely exclusively on OpenAI Realtime's internal conversation history.

If the Realtime session reconnects, reconstruct important context from application-owned state.

In Infer mode, use the best practical mixed-audio approach while retaining application-owned speaker/transcript state.

If Box C cannot be completed without blocking the working A/B application, keep C cleanly disableable and continue development. Do not fake C output.

ERROR HANDLING

The app must degrade gracefully.

If one suggestion provider fails:
show an unobtrusive error in that card and keep the others working.

If STT disconnects:
attempt controlled reconnect and clearly indicate transcript failure.

If Clear mode loses one audio stream:
show a visible warning.

Do not silently misrepresent the session as healthy.

If process loopback fails:
fall back to endpoint loopback where possible.

If retrieval fails:
continue using transcript + meeting state.

If Box C fails:
A and B continue.
